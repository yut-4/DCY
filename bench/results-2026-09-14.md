# DCY exploratory benchmark — 2026-09-14

This is a local pilot, not evidence for “infinite context” or repository repair success. The tests were run on an Intel Core i5-8350U (4 cores/8 threads). The corpus was a cached Tree-sitter `lib/` C/C++ source snapshot at `/home/yuta/.cargo/git/checkouts/tree-sitter-a21c02e4b1d6dd0c/43623ec/lib`. It had 76 indexed files, 893,635 stored source bytes, 884 entities and 896 resolved relations; the SQLite file was ~2.1 MiB. Corpus path and model availability are environment-specific.

## Retrieval-only pilot

18 manually constructed tasks: 8 direct symbol descriptions, 5 paraphrases, 5 multi-hop. Three repeats per task/mode/budget gave 540 query runs. Gold means target function symbols, **not** all evidence needed to answer or patch. Each query starts the CLI process; median latency includes process start and local SQLite access. Cold indexing was ~5.61 s; a repeat over 76 unchanged files was 588 ms (one other warm run was 1.13 s).

| View budget (bytes) | FTS mean gold recall | FTS + 1-hop graph mean gold recall | FTS median | FTS + graph median |
|---:|---:|---:|---:|---:|
| 512 | 44.4% | 44.4% | 17.59 ms | 19.87 ms |
| 1,024 | 58.3% | 58.3% | 17.76 ms | 20.55 ms |
| 2,048 | 63.9% | 63.9% | 17.59 ms | 19.83 ms |
| 4,096 | 72.2% | 72.2% | 17.63 ms | 20.13 ms |
| 8,192 | 72.2% | 77.8% | 17.26 ms | 19.93 ms |

At 512 bytes, the full-gold rate was 38.9% for both modes. Graph traversal added roughly 2–3 ms without recall improvement until 8,192 bytes. The FTS candidate cap limited its mean view to ~3,140 bytes at larger budgets; graph expansion could fill more. This ablation does **not** show DCY outperforming lexical retrieval at the tiny working-set sizes of interest. Paraphrase recall was 20% at 512 bytes and 60% even at 8,192, a clear retrieval failure mode.

**Correction.** The reading that graph traversal adds no recall was an artifact of the packer, not a property of the graph. Measuring the retriever separately from the packer (see the stage attribution pilot below) shows graph expansion raising candidate recall from 72.2% to 83.3%; the identical injected recall in both modes was the greedy packer discarding the difference. After the packer fix, `query` reaches 83.3% injected recall at 4,096 bytes while `query-fts` stays at 72.2%. The numbers in the table above are left unedited as the original measurement; they should not be cited as evidence about graph utility.

```sh
  --db build/tree-sitter-lib.sqlite --tasks bench/tree-sitter-lib-tasks.jsonl \

```

## Model-assisted identification pilot

Nine of the same tasks (first three per category), three conditions per task: no context, FTS, FTS+graph. Local Ollama `qwen2.5:0.5b-instruct`, nominal `num_ctx=512`, 512-byte DCY/FTS view, temperature 0, seed 42. A prompt correction explicitly requested `ts_` names rather than entity IDs; the numbers below are **after** that correction. Input token counts reported by Ollama averaged 111 without context and 354 with either context. The name-identification exact-match rate was **0/9 in all three conditions**; mean gold-name recall was 0% without context and 11.1% with FTS or DCY. No measured input-plus-output count exceeded 512, though that check does not prove the backend never truncated or shifted a prompt.

A smaller control on `qwen3:4b` used three tasks (one per category) and the same 512-token/512-byte settings. Exact-match was **0/3 in all conditions**. Mean recall was 0% no-context, 16.7% FTS, 0% DCY. All nine 4B responses hit the 48-token output limit, so this is mainly evidence that the pilot prompt/output allowance was inadequate, not a clean model comparison. An earlier `qwen3:0.6b` run also had zero exact matches, but used a pre-correction prompt and should not be compared numerically.

The same nine-task `qwen2.5:0.5b-instruct` set was then run through the **real MCP path** (`dcy-mcp`): host benchmark → MCP stdio server → C++ DCY view → one local Ollama API request per task. The MCP view averaged 354.9 model input tokens and 14.9 output tokens; exact-match remained **0/9**, mean gold-name recall **11.1%**, and no observed input-plus-output count exceeded 512. This agrees with the CLI DCY condition in this limited pilot; it does not prove API cost reduction against other retrieval methods. Seven responses gave entity IDs despite the prompt explicitly asking for function names, illustrating the model-interface failure rather than a transport problem.

Reproduce with a locally running Ollama server and installed model:

```sh
python3 bench/llm_identification.py --dcy build/dcy --repo REPO \
  --db build/tree-sitter-lib.sqlite --tasks bench/tree-sitter-lib-tasks.jsonl \
  --model qwen2.5:0.5b-instruct --window 512 --context-bytes 512 \
  --per-category 3 --modes none fts dcy-mcp
```

The model benchmark is not a repair benchmark. It has single-seed, hand-picked tasks, a tiny corpus (~0.9 MB, nowhere near 1M–10M tokens), fixed condition order, local model caching/latency confounds, no exact tokenizer inside DCY, and no answer-quality confidence interval. Median model times are therefore intentionally not presented as an FTS-vs-DCY speed claim.

## Stage attribution pilot

The identification numbers above conflate four different failures. `bench/oracle.py` separates them by measuring, per task: `candidate_recall` (gold in the retriever output at an effectively unbounded budget), `injected_recall` (gold surviving distiller packing at the real budget), `answer_recall` (gold names the model produced), plus two hand-built oracle conditions that bypass retrieval entirely. Nine tasks, `query` mode (FTS + 1-hop graph), 512-byte view, `num_ctx=512`, temperature 0, seed 42.

| Model | Condition | Candidate recall | Injected recall | Answer recall | Exact | Mean input tokens |
|---|---|---:|---:|---:|---:|---:|
| qwen2.5:0.5b-instruct | none | 0.778 | 0.500 | 0.000 | 0/9 | 111.2 |
| qwen2.5:0.5b-instruct | dcy | 0.778 | 0.500 | 0.111 | 0/9 | 354.9 |
| qwen2.5:0.5b-instruct | oracle_ir | — | — | 0.889 | 8/9 | 175.4 |
| qwen2.5:0.5b-instruct | oracle_prose | — | — | 1.000 | 9/9 | 126.8 |
| qwen3:4b | none | 0.778 | 0.500 | 0.000 | 0/9 | 92.2 |
| qwen3:4b | dcy | 0.778 | 0.500 | 0.056 | 0/9 | 335.9 |
| qwen3:4b | oracle_ir | — | — | 0.167 † | 1/9 † | 156.4 |
| qwen3:4b | oracle_prose | — | — | 0.944 | 8/9 | 107.8 |

† Censored by the 48-token output cap; see below. Not a capability measurement.

The oracle conditions hand-build context from the task manifest; they are an upper bound on the renderer and the model, not a DCY result. `oracle_prose` at 1.000 on the 0.5B model rules out model incapacity as the cause of the 0.111 DCY score: this model can do the task when the evidence reaches it in prose.

The `qwen3:4b` oracle_ir cell is **censored by the harness, not a capability measurement**. All nine responses hit the 48-token output cap mid-preamble (`'We are given a goal: "Find the function that..."'`). It must be reported as invalid/truncated; 0.167 is not this model's accuracy on compact IR.

### Refuted hypothesis: compact IR requires a larger model

Before running the oracle, a plausible explanation for the low DCY score was that aggressive ORMT compression shifts decoding cost onto the model, so a 0.5B model would need verbose natural language while a larger model could read dense IR. The prediction was `oracle_prose >> oracle_ir` on the 0.5B model.

The measurement contradicts it. On `qwen2.5:0.5b-instruct`, `oracle_ir` scored 0.889 answer recall and 8/9 exact against `oracle_prose` at 1.000 and 9/9. The single difference is `m03-string`, where the model answered `E381, E382`. That is the entity-ID copying failure, not a failure to decode compact IR. The hypothesis is recorded as refuted rather than removed: on this task set, compact IR costs the 0.5B model at most one task. The ID-placement ablation below confirms the attribution but narrows it — the copying only becomes systematic when many ID-prefixed lines compete for attention, so a single-task gap in a two-line oracle should be read as suggestive, not decisive.

A related consequence: exact match survived audit. If `oracle_prose` gives 9/9 exact, exact match was not hiding semantically correct answers on these identification tasks, and it can stay as the primary metric here. Semantic scoring is still needed for task types where the answer is not a symbol name.

Per-task attribution for the 0.5B `dcy` condition, over the 18-task manifest at 512 bytes:

| Blamed stage | Tasks | Count |
|---|---|---:|
| Retrieval (gold never retrieved) | d01-allocator, p02-abi | 2 |
| Packing (retrieved, not injected) | d03-field, p03-field, m02-recovery | 3 |
| Model/representation (injected, unused) | p01-allocator, m01-edit, m03-string | 3 |
| Correct | d02-abi | 1 |

Retrieval and packing are separable and both lose gold. Across all 18 tasks the retriever finds substantially more than the packer emits:

| Mode | Candidate recall (unbounded) | Injected recall @512 B | Mean candidates | Mean injected entities |
|---|---:|---:|---:|---:|
| query-fts | 72.2% | 44.4% | 23.3 | 4.3 |
| query (FTS + graph) | 83.3% | 44.4% | 79.1 | 4.4 |

This revises the earlier reading that graph traversal adds nothing. Graph expansion raises candidate recall from 72.2% to 83.3%; the identical 44.4% injected recall in both modes is the packer discarding the difference. Eight tasks have gold retrieved but not injected at 512 bytes: d03-field, d07-lookahead, d08-changes, p03-field, p04-tree-edit, p05-capture, and partially m02-recovery and m04-reuse.

The mechanism is in `distiller.hpp`: packing is greedy per entity, taking the first representation level that fits, so the highest-scoring candidate consumes a Detail rendering (~130 bytes with `sha=` and `score=` fields) while later candidates get nothing. The DCY/0.1 header plus goal line consumes 141 of 512 bytes, leaving 371 bytes for evidence — about 4.4 of 79 candidates. A simulated ref-first packing (every candidate at `E<id> <name>`, upgrading only with leftover budget), same retriever and same budget, raises injected recall from 44.4% to 63.9% in both modes. That simulation is a measurement over the existing candidate lists, not an implemented change.

The `answer` column also shows an interface failure independent of recall: in the 0.5B `dcy` condition, six of nine responses were entity IDs such as `E841, E808, E842` despite the prompt forbidding them, including on tasks where the gold entity was injected. Evidence reaching the prompt is not evidence the model can use.

## Packer and renderer fix

The attribution above produced a quantitative prediction: reference-first packing should raise injected recall from 44.4% to 63.9% at 512 bytes without touching retrieval. Two changes were implemented and the prediction was then tested.

`distiller.hpp` packs coverage-first. Pass one admits every candidate it can at `Level::Ref`; pass two spends the remaining budget upgrading admitted entities in score order. Each trial is measured on the fully assembled view, so a non-additive (token-like) meter stays correct. `ormt.hpp` renders name-first: the entity ID moved from a line prefix to a trailing `[ref=E<id>]` tag, because a leading `E187` is a visually privileged token that also looks like a valid answer.

Measured injected recall over all 18 tasks after the change:

| Budget | query-fts before | query-fts after | query before | query after |
|---:|---:|---:|---:|---:|
| 512 | 44.4% | **63.9%** | 44.4% | **63.9%** |
| 1,024 | 58.3% | 72.2% | 58.3% | 72.2% |
| 2,048 | 63.9% | 72.2% | 63.9% | 77.8% |
| 4,096 | 72.2% | 72.2% | 72.2% | 83.3% |
| 8,192 | 72.2% | 72.2% | 77.8% | 83.3% |

The 512-byte figure matches the simulated prediction exactly. Mean injected entities at 512 bytes rose from 4.4 to 10.8. At 4,096+ bytes `query` now reaches 83.3%, equal to its candidate recall — the packer no longer discards anything the graph found, so graph expansion's advantage over FTS is finally visible end to end.

Model-facing effect, nine tasks, `qwen2.5:0.5b-instruct`, same 512-byte/512-token settings:

| Condition | Injected recall before | after | Answer recall before | after |
|---|---:|---:|---:|---:|
| none | 0.500 | 0.611 | 0.000 | 0.000 |
| dcy | 0.500 | 0.611 | 0.111 | **0.500** |
| oracle_ir | — | — | 0.889 | 0.889 |
| oracle_prose | — | — | 1.000 | 1.000 |

Answer recall rose 0.111 → 0.500. Exact match stayed 0/9, because the 0.5B model emits a comma-separated list of plausible neighbours rather than only the gold name; that is an output-precision failure, not a retention failure. The entity-ID copying disappeared completely: **7 of 9 responses contained bare `E<id>` tokens before, 0 of 9 after**. Defining `U = P(gold used | gold injected)` over tasks with non-zero injected recall, `U` rose from 0.222 to 0.818. Evidence that reaches the prompt is now mostly evidence the model uses.

Per-task attribution moved accordingly:

| Blamed stage | Before | After |
|---|---:|---:|
| Retrieval | 2 | 2 |
| Packing | 3 | 2 |
| Representation/model | 3 | 1 |
| Correct | 1 | 4 |

Retrieval is now the largest untouched failure class (d01-allocator, p02-abi — both cases where FTS never surfaces the gold), which is the next thing to attack. The oracle columns are unchanged by design: they bypass retrieval and packing, so they confirm the harness measured the same thing before and after.

`ctest --test-dir build --output-on-failure` runs 4 tests. `tests/distiller_test.cpp` is new and links no SQLite or libclang: it pins budget adherence under additive and non-additive meters, coverage-first admission, leftover-budget upgrading, the `INSUFFICIENT` marker when candidates exist but none fit, and the rule that no rendering level may lead a line with a bare entity ID.

### Entity-ID placement ablation

The before/after comparison confounds two simultaneous changes, so ID placement was isolated directly: same model, same gold evidence, same prompt, varying only where the entity ID appears. `bench/oracle.py --id-ablation` adds four renderings — `id_prefix` (`E187 function name`), `id_suffix` (`function name [ref=E187]`), `id_separate` (ID on its own continuation line) and `no_id`. Each is run twice: gold-only, and `_dense`, where the gold lines are mixed with eight non-gold symbols the retriever actually returned for that goal. 16 tasks, `qwen2.5:0.5b-instruct`.

| Condition | Answer recall | Exact | Entity-ID copy rate |
|---|---:|---:|---:|
| id_prefix | 0.938 | 15/16 | 0.062 |
| id_suffix | 1.000 | 16/16 | 0.000 |
| id_separate | 1.000 | 16/16 | 0.000 |
| no_id | 1.000 | 16/16 | 0.000 |
| id_prefix_dense | 0.625 | 3/16 | **0.250** |
| id_suffix_dense | 0.781 | 2/16 | 0.000 |
| id_separate_dense | 0.625 | 1/16 | 0.000 |
| no_id_dense | 0.875 | 4/16 | 0.000 |

The gold-only rows nearly refute the effect: at one or two evidence lines, placement barely matters (0.938 vs 1.000, a single task). The effect is only visible at realistic density. With eight competing entities, `id_prefix` produces ID-only answers on 4 of 16 tasks (`p02-abi`, `m02-recovery`, `m03-string`, `m05-match-limit` all answered lists like `E381, E382, E86, ...`), while every non-prefix placement produces zero. Answer recall under density is 0.625 for `id_prefix` against 0.875 for `no_id`.

Two honest qualifications. First, the ablation shows that *leading* with the ID is what causes copying — suffix, separate-line and absent placements are indistinguishable on copy rate — but it does not show that suffix beats no-ID on accuracy; `no_id_dense` scores highest, and DCY keeps the ID because `dcy source` needs it, not because it helps the model. Second, `id_prefix` scoring 0.938 gold-only means the earlier claim that ID placement alone explained the `m03-string` oracle_ir failure is only supported at density; in a two-line context that failure is within single-task noise. The mechanism is competition for attention among many ID-prefixed lines, not the presence of an ID as such.

```sh
  --tasks bench/tree-sitter-lib-tasks.jsonl --models qwen2.5:0.5b-instruct \

```

## Checkpoint E1

The packer and renderer results are frozen as a reproducible checkpoint rather than left as prose. `bench/checkpoint.py` reads pilot JSON already on disk — it runs no models, so it cannot silently re-measure and disagree with the report it freezes — and records the recall decomposition, the propagation efficiencies, the failure attribution, `ctest` status and SHA-256 digests of every source and harness file that produced the numbers.

Signal loss is reported as propagation efficiency between stages:

```text
eta_pack     = R_injected / R_candidate     retrieval -> packing
eta_use      = R_answer   / R_injected      packing -> ORMT/model
eta_pipeline = R_answer   / R_candidate     = eta_pack * eta_use
```

| Metric | E0 (greedy, ID-first) | E1 (coverage-first, name-first) | Δ |
|---|---:|---:|---:|
| Candidate recall | 0.778 | 0.778 | +0.000 |
| Injected recall | 0.500 | 0.611 | +0.111 |
| Answer recall | 0.111 | 0.500 | +0.389 |
| `U` (model/renderer) | 0.222 | 0.818 | +0.596 |
| `eta_pack` | 0.643 | 0.786 | +0.143 |
| `eta_use` | 0.222 | 0.818 | +0.596 |
| `eta_pipeline` | 0.143 | 0.643 | +0.500 |
| Entity-ID copies | 7/9 | 0/9 | −7 |
| Tests | — | 4/4 | — |

| Failure stage | E0 | E1 |
|---|---:|---:|
| Retrieval | 2 | 2 |
| Packing | 3 | 2 |
| Representation | 3 | 1 |
| Correct | 1 | 4 |

Candidate recall is identical by construction: neither change touched retrieval. Everything gained came from propagation — `eta_pipeline` rose from 0.143 to 0.643, meaning the pipeline now delivers 64% of what the retriever finds instead of 14%. That is the entire result, stated as a causal decomposition rather than a score.

Two consequences for what comes next. First, retrieval is now the dominant untouched failure class and can be studied nearly in isolation: at 4,096 bytes `query` already satisfies `R_candidate = R_injected = 83.3%`, so the packer no longer masks retrieval changes. Second, `eta_use = 0.818` is a property of the model/renderer pair, so any future renderer change must be re-measured against the same model rather than assumed to transfer.

Frozen artifacts live in `bench/checkpoints/`: `E1.json` (the checkpoint), `E0-pilot.json` and `E1-pilot.json` (the raw pilots it summarises), `E1-id-ablation.json` (the placement ablation). Regenerate with:

```sh
python3 bench/checkpoint.py --id E1 --note "coverage-first packing + name-first ORMT" \
  --baseline-id E0 --before build/oracle.json --after build/oracle-after.json \
  --out bench/checkpoints/E1.json
```

## Retrieval feature ablation

With E1 frozen, retrieval is the dominant remaining failure class. `bench/retrieval_ablation.py` is a Python prototype over the same SQLite index the C++ binary builds; nothing in `src/` is changed by it. It reports candidate recall — gold reachable by the retriever before packing — so the distiller cannot mask a retrieval change. Features are discrete and switched on as sets rather than hand-tuned against the manifest.

### The lexical ceiling bounds every row

Before comparing rankings, the reachable set was measured: entities the FTS query matches at *any* depth. **The ceiling is 83.3% (15/18).** Three tasks — `p02-abi`, `p03-field`, `p04-tree-edit` — share no indexed term with their gold and are unreachable by any reweighting of lexical evidence.

The failure is vocabulary, not ranking. For `p02-abi` ("Which routine exposes the grammar compatibility number?"), the gold body is `uint32_t ts_language_abi_version(const TSLanguage *self) { return self->abi_version; }`. Document frequency of the goal's content terms across 884 entities:

| Term | Documents | In gold |
|---|---:|---|
| routine | 0 | — |
| exposes | 0 | — |
| compatibility | 0 | — |
| grammar | 6 | no |
| number | 12 | no |
| abi | 12 | **yes** |
| version | 71 | **yes** |

The goal and the gold have disjoint vocabulary: the user says "compatibility number", the code says "abi version". `d01-allocator` fails differently — its gold ranks 36th of 91 lexical hits, below the cap of 24, so it *is* a ranking failure and is recoverable. Conflating these two as "retrieval failures" would have sent the weighting work after a task that no weighting can fix.

### Ranking only matters under truncation

At the retriever's current candidate cap of 24 with no truncation, every feature set scores identically (0.722), because recall is measured over the whole returned set and reranking cannot change set membership. The features only pay off when the list is cut — which is what the packer does. Candidate recall at cap 64, truncated to the top 5:

| Feature set | Recall | Full-gold | Missed |
|---|---:|---:|---|
| fts | 0.444 | 0.389 | 11 tasks |
| fts+exact | 0.694 | 0.667 | 6 tasks |
| fts+defn | 0.444 | 0.389 | 11 tasks |
| fts+kind | 0.444 | 0.389 | 11 tasks |
| fts+path | 0.500 | 0.444 | 10 tasks |
| **fts+exact+path** | **0.806** | **0.778** | **4 tasks** |
| fts+exact+defn+kind+path | 0.806 | 0.778 | 4 tasks |
| fts+exact+defn+kind+path+graph | 0.806 | 0.778 | 4 tasks |

At top-10 the same pattern holds (fts 0.639 → fts+exact+path 0.833); at top-20 the gap narrows (0.694 → 0.833) as truncation stops binding.

Three findings, stated conservatively:

1. **`exact` and `path` carry the entire effect.** `fts+exact+path` equals the full six-feature set at every truncation depth tested. `defn` and `kind` are dead weight here: each alone changes nothing, and adding them to `exact+path` changes nothing. A proposed weighted score with six terms is not supported; two are doing the work.
2. **`graph` adds nothing to candidate recall at truncation**, though E1 showed it raises the unbounded candidate set from 72.2% to 83.3%. Graph expansion widens the pool; it does not promote gold into the top of a ranked list, because one-hop neighbours receive a flat score.
3. **0.806 is within 0.03 of the 0.833 lexical ceiling.** Structural reranking has nearly exhausted what lexical retrieval can reach on this manifest. Further gains require non-lexical evidence — the paraphrase tasks are where the remaining loss lives.

Consistency across the three task categories, so the result is not one stratum carrying the average:

| Feature set | direct | paraphrase | multi-hop | all |
|---|---:|---:|---:|---:|
| fts | 0.375 | 0.200 | 0.800 | 0.444 |
| fts+exact | 0.750 | 0.400 | 0.900 | 0.694 |
| fts+exact+path | **1.000** | 0.400 | 0.900 | 0.806 |

Direct tasks go to perfect recall; paraphrase is flat at 0.400 and is exactly the lexically unreachable stratum. This is the honest shape of the result: structural ranking solves direct symbol lookup and does nothing for vocabulary mismatch.

The one remaining reachable miss is `m02-recovery`, which needs two gold symbols; the top-5 contains one of them plus four plausible `ts_parser__*` siblings. That is a multi-gold budget problem, not a ranking error.

### Status: measured, not committed

`H_R` (structural ranking increases candidate recall) is **supported under truncation and not supported without it**. These numbers come from a Python prototype on 18 hand-written tasks. Before any of this enters `src/main.cpp` it needs a larger task set and an end-to-end run through packing and the model, because candidate recall is not packed recall and neither is task success. No checkpoint is claimed for it.

```sh
python3 bench/retrieval_ablation.py --db build/tree-sitter-lib.sqlite \
  --tasks bench/tree-sitter-lib-tasks.jsonl --cap 64 --top 5
```

## Matched-scale pilot: ∂PT/∂VT with constant tasks

The earlier scale pilot changed the task set at each corpus size because tasks whose gold symbols were absent from a smaller index were dropped. That confounds the measurement: `prompt_tokens_mean` depends on goal length, symbol names, paths and the number of entities selected, so a different task distribution at each scale could produce the observed growth even if VT had no causal effect.

`bench/matched_scale.py` fixes this by holding the task set constant: it finds the intersection of tasks scorable at the **smallest** index (100k VT) and runs those exact same 16 tasks against every larger index, with identical goal strings, budget, tokenizer and renderer.

| VT | Budget | Tasks | Injected recall | Prompt tokens (mean) | p95 | VCR |
|---:|---:|---:|---:|---:|---:|---:|
| 100,761 | 512 B | 16 | 0.688 | 166.1 | 174 | 606 |
| 256,215 | 512 B | 16 | 0.625 | 171.3 | 182 | 1,496 |
| 500,697 | 512 B | 16 | 0.625 | 171.8 | 182 | 2,914 |
| 1,002,132 | 512 B | 16 | **0.750** | **166.9** | 178 | **6,005** |
| 100,761 | 2,048 B | 16 | 0.812 | 624.2 | 649 | 161 |
| 256,215 | 2,048 B | 16 | 0.812 | 649.2 | 678 | 395 |
| 500,697 | 2,048 B | 16 | 0.812 | 669.7 | 692 | 748 |
| 1,002,132 | 2,048 B | 16 | **0.875** | **665.7** | 695 | **1,505** |

Prompt growth per 1,000 additional VT tokens:

```text
budget   512 B: +0.00089 tokens / 1k VT   (166.1 -> 166.9 over 100,761 -> 1,002,132 VT)
budget 2,048 B: +0.04604 tokens / 1k VT   (624.2 -> 665.7 over 100,761 -> 1,002,132 VT)
```

**At 512 bytes, a 10× corpus increase costs 0.8 prompt tokens (0.5% growth). At 2,048 bytes, it costs 41.5 tokens (6.6% growth).** Injected recall does not degrade; it *improves* at the largest scale because the bigger index contains more complete context for the same tasks (more relations, fuller bodies). Retrieval p95 stayed in a 19–25 ms band across the whole range.

This is the measurement that supports the decoupling claim without the composition confound. The earlier "5% growth" was an upper bound; the matched experiment shows it is ≤6.6% and as low as 0.5% depending on budget.

Reproduce:

```sh
build/venv/bin/python bench/matched_scale.py --dcy build/dcy \
  --scales 100761=build/corpus-100000.sqlite 256215=build/corpus-250000.sqlite \
  500697=build/corpus-500000.sqlite 1002132=build/corpus-1m.sqlite \

```

Corpus scale in DCY is stated in **tokens under a fixed tokenizer**, not bytes or files. `bench/build_corpus.py` assembles a corpus to a token target using `tiktoken` (`cl100k_base`) and stops when the target is reached, so the same inputs always produce the same corpus. Four indexes were built from shallow clones of tree-sitter, redis, curl and sqlite:

| Target | Actual VT (tokens) | Files | Bytes | Entities | Calls | Cold index |
|---:|---:|---:|---:|---:|---:|---:|
| 100k | 100,761 | 49 | 0.38 MB | 628 | 996 | 1.92 s |
| 250k | 256,215 | 141 | 0.88 MB | 1,208 | 1,595 | 4.06 s |
| 500k | 500,697 | 268 | 1.70 MB | 2,043 | 3,105 | 7.01 s |
| **1M** | **1,002,132** | **431** | **3.29 MB** | **4,251** | **8,171** | **10.19 s** |

The 1M index is 8.5 MB of SQLite. Indexing is roughly linear in corpus size on this hardware (i5-8350U), not superlinear.

### The physical prompt does not grow with the corpus

`bench/scale.py` runs the same tasks against each index at fixed byte budgets and counts prompt tokens with the real tokenizer. The quantity of interest is `d(prompt_tokens)/d(VT)`:

| VT | Budget | Tasks | Injected recall | Prompt tokens (mean) | p95 | VCR | p95 latency |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 100,761 | 512 B | 16 | 0.688 | 166.1 | 174 | 606 | 19.7 ms |
| 256,215 | 512 B | 30 | 0.667 | 170.1 | 185 | 1,506 | 19.4 ms |
| 500,697 | 512 B | 48 | 0.594 | 173.8 | 191 | 2,880 | 20.0 ms |
| 1,002,132 | 512 B | 100 | 0.710 | 174.4 | 188 | **5,747** | 23.0 ms |
| 100,761 | 2,048 B | 16 | 0.812 | 624.2 | 649 | 161 | 23.8 ms |
| 256,215 | 2,048 B | 30 | 0.800 | 643.8 | 672 | 398 | 22.2 ms |
| 500,697 | 2,048 B | 48 | 0.802 | 666.8 | 704 | 751 | 21.6 ms |
| 1,002,132 | 2,048 B | 100 | 0.860 | 695.8 | 740 | **1,440** | 24.8 ms |

Prompt growth per 1,000 additional VT tokens:

```text
budget   512 B: +0.00921 tokens / 1k VT   (166.1 -> 174.4 over 100,761 -> 1,002,132 VT)
budget 2,048 B: +0.07943 tokens / 1k VT   (624.2 -> 695.8 over 100,761 -> 1,002,132 VT)
```

**A 10× corpus increase costs 8.3 prompt tokens at 512 bytes and 71.6 at 2,048 bytes** — 5.0% and 11.5% growth respectively, against 895% corpus growth. Retrieval p95 stayed in a 19–25 ms band across the whole range. Injected recall did not collapse; it was 0.710 at 512 B and 0.860 at 2,048 B on the full 100-task manifest at 1M VT.

Three things this does **not** show. VCR is an addressability ratio, trivially inflatable by adding junk to the corpus, and says nothing about comprehension — 5,747× does not mean the model understands 5,747× more. Injected recall is not task success. The task counts and task distributions differ per scale because a task whose gold symbol is absent from a smaller index is dropped; therefore these rows are an **all-scorable ecological view**, not a causal estimate of prompt growth. The matched-scale section above is the causal estimate for constant tasks.

The falsifiable claim this supports is narrow and is the one worth making: **corpus size is decoupled from physical prompt size within this task regime**, not "infinite context".

## Benchmark v2: 100 generated tasks with a held-out split

The 18-task manifest was hand-written before the retrieval features were designed, which makes the 0.806 result vulnerable to overfitting. `bench/generate_tasks.py` derives tasks mechanically from the index instead, across five strata, and assigns each to a design or held-out split by a hash of its task id, so the split is stable across regenerations and cannot be re-rolled to flatter a result.

| Stratum | Probes | Design | Held-out |
|---|---|---:|---:|
| direct | symbol's own words in a natural phrase | 13 | 7 |
| symbol | the exact symbol name quoted | 10 | 10 |
| path | the module name plus partial symbol words | 12 | 8 |
| paraphrase | words rewritten through a fixed synonym table | 14 | 6 |
| multi-hop | a caller and its callee together | 11 | 9 |

Paraphrase goals are lexically distant **by construction**: the synonym table maps each symbol word to a term chosen from ordinary English rather than from the corpus, so the stratum measures semantic addressability rather than ranking quality.

### `exact+path` replicates on held-out data

Candidate recall at cap 64, truncated to top-5, on the 1M index:

| Feature set | Design | Held-out |
|---|---:|---:|
| fts | 0.617 | 0.650 |
| fts+exact | 0.742 | 0.762 |
| fts+defn | 0.617 | 0.650 |
| fts+kind | 0.617 | 0.650 |
| fts+path | 0.633 | 0.675 |
| **fts+exact+path** | **0.758** | **0.787** |
| fts+exact+defn+kind+path | 0.758 | 0.787 |
| fts+exact+defn+kind+path+graph | 0.758 | 0.787 |

Every conclusion from the 18-task pilot survives on 100 generated tasks with a held-out split, on a corpus 3.7× larger drawn from four different projects:

1. `exact` and `path` carry the whole effect; `fts+exact+path` equals the six-feature set exactly.
2. `defn` and `kind` remain dead weight — identical to plain `fts` when added alone.
3. `graph` adds nothing as a reranker at truncation, while still widening the unbounded pool.

The held-out figures are slightly *higher* than design, which is what a non-overfitted result looks like. The lexical ceiling on this manifest is 88.3% (design) and 90.0% (held-out); `fts+exact+path` at 0.787 is 11 points below its ceiling, so unlike the 18-task pilot there is still lexical headroom left — the earlier "within 0.03 of the ceiling" reading was an artifact of the small manifest.

## Distractor-scale pilot: crecimiento sin cambiar el gold

The matched-scale pilot controls task composition, but larger corpora also add potentially relevant files and graph edges. To isolate contamination by irrelevant data, `bench/build_distractor_corpus.py` keeps the 49-file, 100,761-token tree-sitter base byte-for-byte identical at every scale and adds only files from unrelated redis/curl/sqlite sources. The same 16 tasks whose gold exists in the base are then run at every scale.

| VT | Base gold/files | Added files | Tasks | Injected recall @512 B | Prompt tokens | VCR |
|---:|---:|---:|---:|---:|---:|---:|
| 100,761 | 100,761 / 49 | 0 | 16 | 0.688 | 165.6 | 609 |
| 251,533 | 100,761 / 49 | 75 | 16 | 0.625 | 164.4 | 1,530 |
| 502,651 | 100,761 / 49 | 199 | 16 | 0.625 | 178.2 | 2,820 |
| 1,047,327 | 100,761 / 49 | 348 | 16 | 0.625 | 172.1 | **6,085** |

At 2,048 bytes the corresponding recalls are 0.812, 0.812, 0.750 and 0.812; mean prompts are 624.9, 637.4, 671.6 and 675.2 tokens. From 100k to 1.05M VT, prompt growth is **+6.5 tokens / +3.9% at 512 B** and **+50.3 tokens / +8.0% at 2,048 B**. The 512-byte slope is +0.00687 prompt tokens per 1k added VT; the 2,048-byte slope is +0.05314.

This is the cleanest version of the virtualisation test so far: the gold files and task strings are constant, and the added files are unrelated repositories. Prompt size remains bounded and VCR reaches 6,085:1, but injected recall at 512 B falls from 0.688 to 0.625 and stays there. Therefore the current system is **not distractor-invariant**: extra corpus content can alter lexical ranking/graph expansion and displace useful evidence even when it cannot contain the gold. The claim is narrower than "Recall is constant": physical prompt size is isolated, while retrieval must still be made robust to distractors.

This yields a useful diagnostic:

```text
DR_recall(VT) = Recall(VT) / Recall(base)
512 B: 0.625 / 0.688 = 0.908 at 1.05M distractor VT
```

The 1M scale result should therefore never be reported as prompt isolation alone. It needs both axes: `PT(VT)` for physical isolation and `Recall(VT_irrelevant)` for distractor resistance.

```sh
done
```

## 1M VT with a 500-token model context

The explicit 1M target was run with `qwen2.5:0.5b-instruct`, Ollama `num_ctx=500`, DCY `max_bytes=512`, `num_predict=64`, and 20 held-out tasks (four per generated stratum). This is a model-context test, not only an index test:

```text
VT = 1,002,132 tokenizer-defined corpus tokens
model window = 500 tokens
physical DCY view = 512 bytes
```

The 1M corpus view stayed within the model window: mean input was 334.2 tokens, and input plus the requested 64-token output was at most 406 tokens in the recorded run. Results:

| Candidate recall | Injected recall | Answer recall | Exact | Output truncated |
|---:|---:|---:|---:|---:|
| 0.875 | 0.725 | 0.525 | 1/20 | 5/20 |

This is a **bounded-context result, not a task-success pass**. The model received a 1M-token-addressable index while operating inside `num_ctx=500`, but 45% of the injected gold recall was not reflected in the answer. The model also reproduced `[ref=E<ID>]` tags in 9/20 answers despite name-first rendering, showing that a 500-token window does not eliminate representation contamination at the density of the 1M corpus. Four of the 20 generations hit the deliberately conservative 64-token output cap, so answer recall and exact match are censored for those rows; the input-window bound itself was not violated.

The correct claim is therefore:

> A 1,002,132-token addressable corpus was served to a model configured with a 500-token context window while the physical DCY view remained bounded to 512 bytes. This demonstrates scale isolation of the context transport; it does not demonstrate that a 500-token model can solve arbitrary tasks over a 1M-token corpus.

The failed four-model run remains excluded from conclusions: an earlier Ollama request ended with `RemoteDisconnected` and produced no result artifact. The successful run above is one model, one seed, 20 held-out tasks, and an output cap; broader model comparison needs a stable harness and uncensored output budget.

## What would change the conclusion

Before claiming utility: use unseen repositories of 100k, 1M and 5M+ tokens; task-level answer/patch tests with verified gold evidence; compare the same model and **the same total input/output token and wall-clock budgets** against FTS, graph RAG, repo-map and agentic search; report missing-evidence and retrieval-failure rates. A useful result would be materially higher task success or lower total model/API cost at equal success, not just a large virtual/physical byte ratio.
