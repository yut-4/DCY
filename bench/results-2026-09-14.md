# DCY exploratory benchmark — 2026-09-14

This is a local pilot, not evidence for “infinite context” or repository repair success. The tests were run on an Intel Core i5-8350U (4 cores/8 threads). The corpus was a cached Tree-sitter `lib/` C/C++ source snapshot at `/home/yuta/.cargo/git/checkouts/tree-sitter-a21c02e4b1d6dd0c/43623ec/lib`. It had 76 indexed files, 893,635 stored source bytes, 884 entities and 896 resolved relations; the SQLite file was ~2.1 MiB. Corpus path and model availability are environment-specific.

## Retrieval-only pilot

18 manually constructed tasks: 8 direct symbol descriptions, 5 paraphrases, 5 multi-hop. Three repeats per task/mode/budget gave 540 query runs. Gold means target function symbols, **not** all evidence needed to answer or patch. Each query starts the CLI process; median latency includes process start and local SQLite access. Cold indexing was ~5.61 s; a repeat over 76 unchanged files was 588 ms (one other warm run was 1.13 s).

| View budget (bytes) | FTS mean gold recall | FTS + 1-hop graph mean gold recall | FTS median | FTS + graph median |
|---:|---:|---:|---:|---:|
| 512 | 44.4% | 44.4% | 17.59 ms | 19.87 ms |
| 1,024 | 58.3% | 58.3% | 17.76 ms | 20.55 ms |
| 2,048 | 63.9% | 63.9% | 17.59 ms | 19.83 ms |
| 4,096 | 72.2% | 72.2% | 17.63 ms | 20.13 ms |
| 8,192 | 72.2% | 77.8% | 17.26 ms | 19.93 ms |

At 512 bytes, the full-gold rate was 38.9% for both modes. Graph traversal added roughly 2–3 ms without recall improvement until 8,192 bytes. The FTS candidate cap limited its mean view to ~3,140 bytes at larger budgets; graph expansion could fill more. This ablation does **not** show DCY outperforming lexical retrieval at the tiny working-set sizes of interest. Paraphrase recall was 20% at 512 bytes and 60% even at 8,192, a clear retrieval failure mode.

Reproduce on a local Tree-sitter checkout (replace `REPO` with its `lib` path):

```sh
python3 bench/retrieval.py --dcy build/dcy --repo REPO \
  --db build/tree-sitter-lib.sqlite --tasks bench/tree-sitter-lib-tasks.jsonl \
  --budgets 512 1024 2048 4096 8192 --modes query-fts query \
  --repeats 3 --summary-only
```

## Model-assisted identification pilot

Nine of the same tasks (first three per category), three conditions per task: no context, FTS, FTS+graph. Local Ollama `qwen2.5:0.5b-instruct`, nominal `num_ctx=512`, 512-byte DCY/FTS view, temperature 0, seed 42. A prompt correction explicitly requested `ts_` names rather than entity IDs; the numbers below are **after** that correction. Input token counts reported by Ollama averaged 111 without context and 354 with either context. The name-identification exact-match rate was **0/9 in all three conditions**; mean gold-name recall was 0% without context and 11.1% with FTS or DCY. No measured input-plus-output count exceeded 512, though that check does not prove the backend never truncated or shifted a prompt.

A smaller control on `qwen3:4b` used three tasks (one per category) and the same 512-token/512-byte settings. Exact-match was **0/3 in all conditions**. Mean recall was 0% no-context, 16.7% FTS, 0% DCY. All nine 4B responses hit the 48-token output limit, so this is mainly evidence that the pilot prompt/output allowance was inadequate, not a clean model comparison. An earlier `qwen3:0.6b` run also had zero exact matches, but used a pre-correction prompt and should not be compared numerically.

The same nine-task `qwen2.5:0.5b-instruct` set was then run through the **real MCP path** (`dcy-mcp`): host benchmark → MCP stdio server → C++ DCY view → one local Ollama API request per task. The MCP view averaged 354.9 model input tokens and 14.9 output tokens; exact-match remained **0/9**, mean gold-name recall **11.1%**, and no observed input-plus-output count exceeded 512. This agrees with the CLI DCY condition in this limited pilot; it does not prove API cost reduction against other retrieval methods. Seven responses gave entity IDs despite the prompt explicitly asking for function names, illustrating the model-interface failure rather than a transport problem.

Reproduce with a locally running Ollama server and installed model:

```sh
python3 bench/llm_identification.py --dcy build/dcy --repo REPO \
  --db build/tree-sitter-lib.sqlite --tasks bench/tree-sitter-lib-tasks.jsonl \
  --model qwen2.5:0.5b-instruct --window 512 --context-bytes 512 \
  --per-category 3 --modes none fts dcy-mcp
```

The model benchmark is not a repair benchmark. It has single-seed, hand-picked tasks, a tiny corpus (~0.9 MB, nowhere near 1M–10M tokens), fixed condition order, local model caching/latency confounds, no exact tokenizer inside DCY, and no answer-quality confidence interval. Median model times are therefore intentionally not presented as an FTS-vs-DCY speed claim.

## MCP boundary check

`ctest --test-dir build --output-on-failure` now includes an MCP stdio smoke test: lifecycle, tool listing, bounded view, exact UTF-8 source, stale-generation rejection, observation and goal completion. It passed 3/3 tests total. The MCP server itself performs zero model API calls; no host-to-model API gateway or end-to-end API traffic measurement exists yet. Its existence alone cannot establish an API cost reduction.

## What would change the conclusion

Before claiming utility: use unseen repositories of 100k, 1M and 5M+ tokens; task-level answer/patch tests with verified gold evidence; compare the same model and **the same total input/output token and wall-clock budgets** against FTS, graph RAG, repo-map and agentic search; report missing-evidence and retrieval-failure rates. A useful result would be materially higher task success or lower total model/API cost at equal success, not just a large virtual/physical byte ratio.
